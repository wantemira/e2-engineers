# AI-Buddy

[Первая линия помощи](docs/team-help.md): ответы по разделам командных документов, инструкции доступов и каталог профильных помощников. HR, отпуска и БД — демонстрационные примеры; новый адресат добавляется конфигурацией и Markdown-профилем. Перед каждым сообщением Buddy ищет по локальным материалам через MCP, для учебного orders читает mock-окружение и CI, затем уточняет недостающие данные. По просьбе пользователя готовит редактируемое обращение наставнику с результатами проверок.

По умолчанию приложение работает в `Demo Mode` без ключа модели. В отдельном `Live LLM`-режиме модель выбирает разрешённый сценарий и анализирует PR с фактическими инструкциями skill и контекстом команды. Настройка, ограничения и результаты контрольных Live-прогонов — в [документации LLM](docs/llm.md). Для проверенного маршрута OpenRouter перед записью задайте `LLM_TIMEOUT=45s` в серверном `.env` и выполните контрольный запрос: доступность внешнего провайдера не гарантируется автоматическими тестами.

Self-Review включает [разбор тестов и mock CI](docs/ci.md): напишите «Проверь PR #17 и запусти тесты» или нажмите «Имитировать запуск CI и обновить анализ» в отчёте. Показываются конкретные тесты, ошибки, логи, SHA и ID запуска. Исходный PR имеет FAILED, исправленный — PASSED; код PR инструмент не выполняет.

## Проверка и сдача

Полный маршрут с командами, текстом видео и списком файлов — [пошаговая инструкция](docs/submission.md). Проверка и сбор отчётов в PowerShell из корня проекта (нужны Go, Node.js и Microsoft Edge):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\prepare-submission.ps1
```

После успешных тестов и покрытия строк **больше 80%** для backend и frontend появится `artifacts/submission-<дата>.zip`: HTML/XML/LCOV-отчёты, браузерный отчёт, логи и SHA проверенного коммита. Скрипт не вызывает живую модель и не запускает Docker. Live и запуск приложения проверьте перед записью по инструкции. `.env` и ключи в архив не входят. PDF-презентацию и видеодемо приложите отдельно; поведение агента описано в [SDD](docs/sdd.md).

## Запуск через Make

Нужны GNU Make и запущенный Docker с Compose. Из корня проекта:

```sh
make up
```

Compose собирает Go API и фронтенд, проверяет готовность обоих сервисов и открывает AI-Buddy на `http://127.0.0.1:5173/`. Повторный `make up` обновляет существующий стек. Если порт занят другим приложением, задайте свободный, например `make up BUDDY_PORT=5180`, или укажите порт в корневом `.env` по примеру `.env.example`.

| Команда | Действие |
| --- | --- |
| `make restart` | Останавливает стек, освобождает порт и создаёт контейнеры заново с сохранением истории. |
| `make down` | Останавливает стек и освобождает порт. |
| `make reset` | Удаляет историю, проверки и квитанции из тома Compose, выбирает исходный PR, сбрасывает CI и запускает чистый экземпляр. |
| `make build` | Собирает образы. |
| `make ps` | Показывает состояние сервисов. |
| `make logs` | Показывает логи сервисов. |
| `make config` | Проверяет конфигурацию Compose. |
| `make demo-reset` | Возвращает исходный PR, базовые CI и mock-окружение без удаления истории и квитанций. |
| `make demo-initial` | Выбирает исходный PR, сохраняя историю проверок. |
| `make demo-fixed` | Выбирает исправленную версию PR, сохраняя историю. |
| `make demo-ci CHECKS=PASSED` | Задаёт статус CI выбранной версии. Допустимы UNKNOWN, RUNNING, FAILED и PASSED. |

Compose хранит состояние в именованном томе. При запуске без Docker Go API использует локальную папку `.data/`.

## Запуск без Docker

Запустите Go API и фронтенд в отдельных терминалах из корня проекта. Нужны Go 1.26.2 и Node.js 22.12+.

```powershell
cd backend
go run ./cmd/api
```

```powershell
cd frontend
npm ci
npm run dev
```

Откройте [AI-Buddy](http://127.0.0.1:5173/) и напишите «Как получить доступ к репозиторию?» или «Проверь PR #17». После проверки можно спросить «Объясни замечание 1» и подтвердить отправку наставнику.

Ответы на командные вопросы в Demo формируются локально по файлам `teams/demo-backend`. Самопроверка в Demo вызывает mock внутреннего скилла через MCP; в Live анализ с инструкциями skill выполняет модель. Источник результата явно отмечен в чате. Данные PR, CI и квитанция поступают из локального Git-сервиса через MCP. Для проверки исправленной версии выполните `make demo-fixed`, затем нажмите «Обновить AI-анализ». Статусы CI имитируют результат внешней проверки и отображаются после нового запуска самопроверки.

Переключатели демо хранятся в `demo.json` рядом с данными приложения в томе Compose. При запуске без Docker выполните из `backend`:

```sh
go run ./cmd/demo -revision fixed
go run ./cmd/demo -checks FAILED
go run ./cmd/demo -reset
```

Эти команды используют `DATA_DIR` либо папку `.data/` в корне проекта. Для своего расположения данных передайте `-data <путь>`. Команда `demo -reset` возвращает исходный PR и базовые CI fixtures (initial FAILED, fixed PASSED), сохраняя диалог и квитанции. Полный сброс экземпляра Compose выполняется через `make reset`.

При запуске без Docker API слушает `127.0.0.1:8080`. В Compose браузер обращается к API через прокси фронтенда. Сессия восстанавливается по cookie. Незавершённые операции продолжают опрос по сохранённому ID. При неизвестном результате отправки после перезагрузки доступно «Уточнить результат» с исходными версией PR и ключом действия. Интеграция использует подготовленный PR и локальную квитанцию назначения ревью. Ключ модели для запуска не нужен.

Запрос ревью привязан к SHA и наставнику: повторная отправка той же версии возвращает существующую квитанцию, а после обновления PR и новой самопроверки требуется отдельное подтверждение. Старые квитанции остаются в истории. После временной ошибки чтения или самопроверки кнопка «Повторить» запускает прежнюю операцию с исходным ключом, не добавляя сообщение повторно. Неизвестный результат отправки уточняется отдельно с исходными параметрами.

Новые отчёты сохраняют diff проверенной версии PR. Ссылка в замечании открывает нужную строку, даже если PR уже обновился. Чтобы получить такие ссылки для отчёта, сохранённого до этого изменения, запустите проверку повторно.

Профильные помощники задаются в `teams/demo-backend/context.json` → `help.assistants`: имя, тема, раздел профиля и необязательный URL. По умолчанию используются работающие локальные demo-профили, сообщения ботам не отправляются. `people_agent_url` сохранён для прежнего fallback без `team-help`; новые направления подключайте через каталог, описанный в [инструкции](docs/team-help.md).

## Учебный сервис стажёра

Спросите в чате «Где тестовое окружение?» — AI-Buddy покажет задание, команды запуска, статус mock-окружения и CI для выбранного SHA PR №17. Ответ сохраняется в истории и содержит ссылку на [инструкцию](teams/demo-backend/environment-guide.md).

В `training/orders` находится самостоятельный Go-сервис с POST /orders и GET /healthz. Задание — сохранить причину ошибки хранилища. Регрессионный тест начальной версии намеренно падает. После исправления `training/orders/internal/orders/service.go` повторите проверку. Для сравнения доступен эталон с build tag `solution`.

```sh
make training-up
make training-test
make training-solution-test
make training-down
```

Учебный сервис доступен по `http://127.0.0.1:8081/healthz`. Порт задаётся переменной `BUDDY_TRAINING_PORT`. Тесты выполняются в отдельном контейнере с отключённой сетью. После изменения кода команды пересобирают соответствующий образ.

Без Docker перейдите в `training/orders`, запустите `go run ./cmd/api`, затем в другом терминале — `go test ./...`. Эталон проверяется командой `go test -tags solution ./...`. Нужен Go 1.26.2. Проверки конкурентного доступа и отмены контекста входят в тесты упражнения.

Статусы окружения и CI в чате являются результатом mock-инструмента. Команды `make demo-environment ENVIRONMENT=READY` и `make demo-ci CHECKS=PASSED` управляют демонстрацией. Фактический результат учебных тестов виден в терминале. Для нового ответа со статусом напишите «Покажи результат тестов». Команда `make reset` очищает историю и возвращает исходный PR, базовые CI fixtures и STOPPED для mock-окружения.

## Тесты и покрытие

Из `frontend`:

```sh
npm ci
npx playwright install chromium
npm run test:e2e
npm run test:coverage
```

Браузерные тесты запускают Go API и Vite на портах 18080 и 4173 и используют временные данные. Сценарии проверяют путь от сообщения до квитанции, переход к строке diff, повторную проверку, восстановление истории и действия в чате. Для запуска в установленном Microsoft Edge задайте `BUDDY_BROWSER_CHANNEL=msedge` в окружении. Отчёт Playwright находится в `frontend/playwright-report/index.html`, объединённое покрытие Vitest и Playwright — в `frontend/coverage/index.html`. Порог по **строкам** фронтенда — строго больше 80%.

Из корня проекта для backend (нужен Docker):

```sh
docker build --target build -f backend/Dockerfile -t ai-buddy-coverage-go .
docker run --rm --network none -v "$PWD:/workspace" -w /workspace/backend ai-buddy-coverage-go \
  go test ./... -timeout=60s -coverpkg=./... -coverprofile=/workspace/backend/coverage.out
```

`coverage.out` создаётся в `backend/`. Для отчёта **по строкам**, включая `cmd/` и `internal/`, установите [gocover-cobertura v1.5.0](https://github.com/boumenot/gocover-cobertura) и запустите из `backend`:

```sh
go install github.com/boumenot/gocover-cobertura@v1.5.0
gocover-cobertura -strict -ignore-non-code-lines -by-files < coverage.out > coverage.xml
```

Итоговые `lines-covered` и `lines-valid` находятся в корневом элементе `backend/coverage.xml`. Прогон 16.11.2026 после Live-исправлений: 2512/2983 строк backend (84,21%) и 398/453 frontend (87,85%). Перед сдачей после новых изменений пересчитайте проценты и приложите отчёты. Учебный модуль `training/orders` отдельный и имеет намеренно падающий исходный тест; его эталон запускается `make training-solution-test`. Карта требований и проверок — [SDD](docs/sdd.md). Сценарий записи — [демо](docs/demo.md). Контракт HTTP описан в `frontend/README.md`.

## Слои backend

- `cmd/api` собирает зависимости и запускает HTTP-сервер и обработчик фоновых операций.
- `internal/transport/httpapi` разбирает HTTP-запросы, управляет cookie и формирует ответы.
- `internal/service` обрабатывает команды чата, проверку PR и отправку на ревью. Здесь определены интерфейсы для хранилища и интеграций.
- `internal/repository` сохраняет сессии, историю и очередь операций. `internal/domain` содержит общие модели.
- `internal/assistant` отвечает на командные вопросы; анализатор ревью используется внутри mock внутреннего скилла.
- `internal/teamconfig` и `internal/skillcatalog` загружают командный контекст, каталог скиллов и привязки возможностей.
- `internal/integration/mcpgit` и `internal/integration/mcpskills` реализуют Git-инструменты и mock внутренних скиллов; `mcptransport` содержит общий авторизованный транспорт.

Правила подключения новых скиллов, контракты, пример добавления без Go-правок и ограничения mock описаны в [инструкции](docs/skills.md).

## Сообщения коммитов

Используем формат Conventional Commits `тип: короткое действие`. В одном коммите собираем одну логически связанную правку. После двоеточия пишем с маленькой буквы и без точки в конце.

| Тип | Когда использовать | Пример |
| --- | --- | --- |
| `feat` | Новая возможность | `feat: добавить самопроверку PR` |
| `fix` | Исправление ошибки | `fix: восстановить историю чата после перезагрузки` |
| `docs` | Документация | `docs: описать локальный запуск` |
| `test` | Тесты | `test: проверить повторную отправку на ревью` |
| `refactor` | Изменение структуры кода с сохранением поведения | `refactor: вынести обработку команд из HTTP-слоя` |
| `chore` | Служебные правки | `chore: добавить правила игнорирования файлов` |
