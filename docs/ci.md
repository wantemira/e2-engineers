# PR Self-Review и mock CI

CI синтетический: инструмент не компилирует и не запускает код PR. Результаты подготовлены по примеру доверенного учебного сервиса `training/orders`, реальные тесты которого запускаются отдельно через `make training-test` / `make training-solution-test`.

## Прохождение сценария

1. Запустите приложение через `make up`. Если ранее задавались ручные статусы CI, сбросьте demo overrides по командам ниже. Для полностью чистого Compose-экземпляра используйте `make reset` (эта команда удаляет историю).
2. Напишите «Проверь PR #17 и запусти тесты». Backend получает PR и SHA, вызывает `run_pull_request_checks`, затем skill анализирует diff и результат CI для той же версии.
3. Исходная версия показывает `FAILED`: `TestCreateRepositoryError` ожидает обёрнутую ошибку, но получает `create order failed`. Отчёт объясняет потерю причины, предлагает `%w` и тест с `errors.Is`.
4. Спросите «Почему упал тест?» или «Какой тест добавить?». В Demo объяснение берётся из сохранённой оценки CI; Live получает текущий отчёт с тестами/логами.
5. Нажмите «Имитировать запуск CI и обновить анализ»: появится новый ID запуска и отдельный отчёт. Простой «Обновить AI-анализ» повторяет анализ с последним CI без нового запуска.
6. Выполните `make demo-fixed` и снова запустите mock CI. Исправленная ревизия вернёт `PASSED` и тест сохранения ошибки. Старые отчёты сохранят исходные SHA, ID и логи, в том числе после перезапуска.
7. Отправка наставнику остаётся отдельным подтверждённым действием. Красный CI не означает, что Buddy одобрил PR; решение о ревью принимает человек.

Для сброса только demo overrides без очистки истории в Compose можно выполнить `docker compose run --rm --no-deps --entrypoint ai-buddy-demo backend -root /app -reset`. Сохранённые запуски и отчёты остаются; полный сброс — `make reset`.

## Контракт

`Checks` сохраняет прежние `status` и `label`, добавляя:

```json
{
  "status": "FAILED",
  "label": "Не прошёл TestCreateRepositoryError",
  "pr_number": 17,
  "head_sha": "проверяемый SHA",
  "run_id": "CI-идентификатор",
  "source": "MOCK",
  "created_at": "2026-11-15T00:00:00Z",
  "tests": [
    {"name": "TestCreateRepositoryError", "status": "FAILED", "error": "expected wrapped storage error, got create order failed"}
  ],
  "logs": "--- FAIL: TestCreateRepositoryError\nFAIL"
}
```

MCP:

- `get_pull_request_checks(number, head_sha)` читает последний сохранённый результат текущей версии либо её fixture.
- `run_pull_request_checks(number, head_sha, action_key)` немедленно возвращает и сохраняет синтетический результат. Новый ключ создаёт новый запуск; повтор исходного ключа возвращает исходный результат. Подмена SHA при том же ключе — `IDEMPOTENCY_CONFLICT`.

Контроль пользователя/PR и проверка актуального SHA выполняются Git mock. Новый запуск старой ревизии — `STALE_HEAD`. Точный повтор ранее выполненного запуска возвращает его исходный результат даже после смены версии — новый запуск при этом не создаётся.

Приложение передаёт серверный ID операции как `action_key`, модель его не выбирает. Запуски и последний результат сохраняются в Git JSON-состоянии. Потеря ответа, повтор после временного сбоя и перезапуск не создают дубль для того же действия. Сохранённый review run содержит собственный снимок CI; последующие запуски его не изменяют.

HTTP: `POST /api/v1/self-reviews` принимает `{ "pr_ref": "17", "run_checks": true }`. Как и раньше, нужен `Idempotency-Key`, ответ — `202` и ID фоновой операции. Отсутствие `run_checks` означает только анализ. Исторические отчёты с `status/label` остаются читаемыми.

`assessment.ci` содержит разбор CI, `assessment.suggested_tests` — конкретные рекомендуемые кейсы. В Live они формируются моделью по данным инструмента; в Demo анализатор связывает известный регрессионный тест с видимой потерей причины ошибки. При недостатке данных причина не выдумывается.

Результаты с неверным SHA/PR/источником, неизвестными статусами, противоречием PASSED и failed test или чрезмерными логами отклоняются. Лимиты: 100 тестов, 4 КБ сообщения ошибки теста, 16 КБ лога. Логи отображаются как текст и являются недоверенными данными для LLM.

## Управление демонстрацией

По умолчанию исходный PR — `FAILED`, исправленный — `PASSED`. `demo -reset` возвращает эти базовые результаты. `make demo-ci CHECKS=UNKNOWN|RUNNING|FAILED|PASSED` остаётся ручной симуляцией статуса выбранной ревизии; она убирает тесты/логи fixture, чтобы не показывать PASSED рядом со старым failed test. Для содержательного failed → passed сценария переключайте ревизию и запускайте CI, а не меняйте статус вручную.

## Проверки

Автотесты покрывают привязку CI к SHA, права, идемпотентность, сохранение при перезапуске, потерю ответа и безопасный retry, combined PR+tests, снимки истории, проверку DTO и передачу логов Live-адаптеру через тестовый API. Браузерный сценарий проходит failed → объяснение → rerun → fixed passed → история → перезагрузка. Автотесты Live используют тестовый API модели.
