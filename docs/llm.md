# Live LLM: настройка и SDD

Провайдер и модель пока не выбраны. Реализован серверный адаптер OpenAI-совместимого Chat Completions API. Автотесты используют локальный тестовый API: это проверка контракта и приложения, а не качества настоящей модели.

## Режимы и настройка

- `BUDDY_MODE=demo` (по умолчанию): прежние детерминированные ответы и MCP mock ревью. Запросов к LLM нет, даже если задан ключ.
- `BUDDY_MODE=live`: запросы обрабатывает модель. Неполная конфигурация останавливает запуск; сбой API не подменяется Demo-ответом.

UI получает режим/модель из `/api/v1/workspace.assistant` и показывает `Demo Mode` или `Live LLM`. Ключ и API URL в ответ не входят. Режим меняется на сервере с перезапуском.

Когда появится доступ к модели, создайте корневой `.env` по `.env.example` (если файл уже есть, сохраните его значения). Настройте:

```dotenv
BUDDY_MODE=live
LLM_PROVIDER=openai-compatible
LLM_BASE_URL=https://YOUR_PROVIDER/v1
LLM_MODEL=YOUR_MODEL_ID
LLM_API_KEY=YOUR_SERVER_API_KEY
LLM_TIMEOUT=20s
```

Затем выполните `make up`. Для возврата установите `BUDDY_MODE=demo` и снова выполните `make up`. Очистка истории не нужна.

Адаптер добавляет к базовому URL `/chat/completions`. Нужна поддержка function tools с JSON Schema, `strict`, `tool_choice=required`, `parallel_tool_calls=false` и `max_completion_tokens`. Совместимость конкретного провайдера проверяется живым smoke test; надпись «OpenAI-compatible» сама по себе её не гарантирует. HTTP допускается для локального API; если он не требует ключа, задайте непустой фиктивный ключ, например `local-only`.

Без Docker экспортируйте переменные перед `go run ./cmd/api` из `backend`: приложение самостоятельно `.env` не читает. В Docker API URL должен быть доступен из контейнера; `127.0.0.1` — сам контейнер.

Ключ хранится только на backend, не в `VITE_*` и не в Git. Сырые ответы провайдера при ошибках не выводятся в журнал и не возвращаются пользователю. HTTP redirects не выполняются. Используются только синтетические материалы и PR.

Протокол: [официальная документация function calling](https://developers.openai.com/api/docs/guides/function-calling). SDK конкретного провайдера не требуется.

## Выбор сценария

1. Сохраняемая операция `message` загружает team context, подключённые skills с фактическим Markdown, последние 20 сообщений и текущий отчёт PR.
2. Модель возвращает ровно один function call:
   - `answer_question(text, document_ids, mentor_draft)` — ответ, уточнение, объяснение замечания или черновик человеку. Ссылки строятся сервером только для существующих документов.
   - `run_pr_self_review(pr_ref)` — полный read-only сценарий самопроверки, включающий чтение доступного CI.
   - `get_training_status(pr_ref)` — чтение mock-окружения/CI при наличии training-конфигурации.
   - `execute_message_skill(skill_id)` — только подключённый информационный skill. Его исполнение пока остаётся mock и так маркируется.
3. Backend отклоняет неизвестные функции, лишние поля/identity и неподключённые skills. PR проходит прежние проверки репозитория/пользователя и прав в Git MCP.
4. Только успешное исполнение сохраняет ответ/отчёт. В сообщении остаются `agent.model` и `agent.tool`; в журнале — только имена сценария и модели, без prompt/diff/ключей.

Это ограниченный выбор сценария, а не универсальный агентный цикл. `request_pull_request_review` среди функций модели отсутствует. Кнопки self-review/recheck сохраняют прежний путь, но в Live анализ выполняет LLM SkillRunner.

## Применение PR skill

Live-реализация `SkillRunner` заменяет mock-исполнителя для `pr-review.v1`, сохраняя контракт результата:

1. Сверяет target/version/contract и точное содержимое инструкций с подключённым skill команды.
2. Получает разрешённый PR и CI через Git MCP от имени demo-пользователя, проверяет SHA и лимит diff.
3. Передаёт фактический `SKILL.md`, документы, правила, задачу, diff и полученный CI модели. PR/логи — недоверенные данные; они не определяют полномочия.
4. Получает `submit_review` с замечаниями и границами анализа. Сервер нормализует ID и ссылки на правила; PR/SHA/CI/метаданные исполнения модель не задаёт.
5. Прежний валидатор проверяет контракт, позиции в diff, тип замечания, известные правила и актуальность SHA после анализа. Неверный результат не становится отчётом.
6. Сохраняет `skill_execution.source=LLM`, модель, версии/target, ID исполнения, хеш Markdown и `rules_sha256` (снимок документов/правил). Diff проверенной версии сохраняется как раньше.

Это наш LLM-адаптер, не заявленная интеграция с неизвестным AI-сервисом Авито. Git/CI остаются синтетическими. Demo использует `/internal/skills` и локальный анализатор. Изменение текста skill отражается в следующем prompt и его сохранённом хеше.

## Ошибки и подтверждения

Один LLM-вызов ограничен `LLM_TIMEOUT` (1–25 секунд); PR-сообщение обычно требует двух вызовов: выбор сценария и анализ. Операция приложения ограничена 60 секундами, UI продолжает асинхронный опрос.

| Код | Поведение |
|---|---|
| `LLM_UNAVAILABLE` | Сеть, 429/408/5xx: повтор исходной операции с прежними ID/ключом. |
| `LLM_TIMEOUT` | Модель не успела ответить: доступен повтор. |
| `LLM_CONFIGURATION` | Ключ, права или несовместимый запрос/модель: исправить серверную конфигурацию. |
| `LLM_INVALID_RESULT` | Некорректный JSON/function call, запрещённая функция/источник: доступен повтор без локальной подмены. |
| `SKILL_INVALID_RESULT` | Не прошли существующие проверки позиций, правил или контракта. |

Отправка наставнику выполняется только отдельным подтверждённым действием. Права, SHA, наставник и идемпотентность проверяются вне модели; неизвестный результат уточняется по исходной операции.

## Проверка

`go test ./...` покрывает API/конфигурацию/ошибки/отмену и путь HTTP → очередь → Live-адаптер → Git MCP → structured report → подтверждённая квитанция. Проверяются передача изменённого skill, запрет чужого PR, выдуманной строки и инструмента записи. Автотесты не вызывают платный API. Браузерные тесты явно запускают Demo независимо от окружения.

Ручной smoke test после выбора провайдера:

1. Запустить Live с настоящим доступом, проверить ярлык и ответ по правилам со ссылкой.
2. Свободной формулировкой попросить проверить PR #17; проверить `agent.tool`, `skill_execution.source/model`, хеши и замечания по diff.
3. Уточнить замечание, затем проверить исправленную версию и подтвердить отправку: квитанция должна содержать новый SHA.
4. Попробовать чужой PR и отправку без кнопки: защищённые данные/квитанция не появляются.
5. Временно указать неверный ключ: появляется ошибка, а не Demo-ответ.

Этот smoke test **пока не выполнен**: реальные провайдер, модель и ключ не предоставлены. Контрактные тесты не доказывают качество ответов настоящей модели.

## Границы пакета LLM

CI пока содержит `status/label`: модель не может объяснить отсутствующий лог или запустить CI. Содержательный mock CI, `run_pull_request_checks`, конкретный каталог доступов и готовый People-handoff — отдельные пакеты ТЗ v0.4. Для PR+тесты Live выбирает self-review с чтением CI; повторный запуск до подключения инструмента не обещается.
