# Подключение LLM

Серверный адаптер OpenAI-совместимого Chat Completions API выбирает разрешённый сценарий и анализирует PR с инструкциями skill и контекстом команды. Автотесты используют локальный тестовый API.

## Режимы и настройка

- `BUDDY_MODE=demo` (по умолчанию): детерминированные ответы и MCP mock ревью. Запросов к LLM нет, даже если задан ключ.
- `BUDDY_MODE=live`: запросы обрабатывает модель. Неполная конфигурация останавливает запуск; сбой API не подменяется Demo-ответом.

UI получает режим/модель из `/api/v1/workspace.assistant` и показывает `Demo Mode` или `Live LLM`. Ключ и API URL в ответ не входят. Режим меняется на сервере с перезапуском.

Для Live-режима создайте корневой `.env` по `.env.example` (если файл уже есть, сохраните его значения). Пример конфигурации OpenRouter:

```dotenv
BUDDY_MODE=live
LLM_PROVIDER=openai-compatible
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_MODEL=openrouter/free
LLM_API_KEY=YOUR_SERVER_API_KEY
LLM_TIMEOUT=45s
```

Затем выполните `make up`. Для возврата установите `BUDDY_MODE=demo` и снова выполните `make up`. Очистка истории не нужна.

Адаптер добавляет к базовому URL `/chat/completions`. Нужна поддержка function tools с JSON Schema, `strict`, `tool_choice=required`, `parallel_tool_calls=false` и `max_completion_tokens`. Совместимость конкретного провайдера проверяется запросом к выбранной модели; надпись «OpenAI-compatible» сама по себе её не гарантирует. HTTP допускается для локального API; если он не требует ключа, задайте непустой фиктивный ключ, например `local-only`.

Без Docker экспортируйте переменные перед `go run ./cmd/api` из `backend`: приложение самостоятельно `.env` не читает. В Docker API URL должен быть доступен из контейнера; `127.0.0.1` — сам контейнер.

Ключ хранится только на backend, не в `VITE_*` и не в Git. Сырые ответы провайдера при ошибках не выводятся в журнал и не возвращаются пользователю. HTTP redirects не выполняются. Используются только синтетические материалы и PR.

Протокол: [официальная документация function calling](https://developers.openai.com/api/docs/guides/function-calling). SDK конкретного провайдера не требуется.

## Выбор сценария

1. Сохраняемая операция `message` загружает team context, подключённые skills с фактическим Markdown, последние 20 сообщений и текущий отчёт PR.
2. Модель возвращает ровно один function call:
   - `answer_question(text, document_ids, mentor_draft)` — ответ, уточнение, объяснение замечания или черновик человеку. Ссылки строятся сервером только для существующих документов.
   - `run_pr_self_review(pr_ref, run_checks)` — самопроверка с чтением CI; `run_checks=true` по просьбе пользователя запускает новый mock CI и анализирует его в том же отчёте, без исполнения кода PR.
   - `find_team_help(kind, target_id)` — инструкция доступа, профильный помощник или черновик наставнику из каталога команды.
   - `search_team_knowledge(query, purpose)` — поиск по командным материалам и доступная mock-диагностика.
   - `get_training_status(pr_ref)` — чтение mock-окружения/CI при наличии training-конфигурации.
   - `execute_message_skill(skill_id)` — только подключённый информационный skill. Его исполнение пока остаётся mock и так маркируется.
3. Backend отклоняет неизвестные функции, лишние поля/identity и неподключённые skills. PR проходит проверки репозитория/пользователя и прав в Git MCP.
4. Только успешное исполнение сохраняет ответ/отчёт. В сообщении остаются `agent.model` и `agent.tool`; в журнале — только имена сценария и модели, без prompt/diff/ключей.

Это ограниченный выбор сценария, а не универсальный агентный цикл. `request_pull_request_review` среди функций модели отсутствует. Кнопки самопроверки и повторного анализа используют тот же контракт; в Live анализ выполняет LLM SkillRunner.

## Применение PR skill

Live-реализация `SkillRunner` заменяет mock-исполнителя для `pr-review.v1`, сохраняя контракт результата:

1. Сверяет target/version/contract и точное содержимое инструкций с подключённым skill команды.
2. Получает разрешённый PR и CI через Git MCP от имени demo-пользователя, проверяет SHA и лимит diff.
3. Передаёт фактический `SKILL.md`, документы, правила, задачу, diff и полученный CI модели. PR/логи — недоверенные данные; они не определяют полномочия.
4. Получает `submit_review` с замечаниями и границами анализа. Сервер нормализует ID и ссылки на правила; PR/SHA/CI/метаданные исполнения модель не задаёт.
5. Валидатор проверяет контракт, позиции в diff, тип замечания, известные правила и актуальность SHA после анализа. Неверный результат не становится отчётом.
6. Сохраняет `skill_execution.source=LLM`, модель, версии/target, ID исполнения, хеш Markdown и `rules_sha256` (снимок документов/правил). Diff проверенной версии сохраняется как раньше.

Это наш LLM-адаптер, не заявленная интеграция с неизвестным AI-сервисом Авито. Git/CI остаются синтетическими. Demo использует `/internal/skills` и локальный анализатор. Изменение текста skill отражается в следующем prompt и его сохранённом хеше.

## Ошибки и подтверждения

`LLM_TIMEOUT` задаёт время одной попытки (1–45 секунд, по умолчанию 45). Сетевой сбой, таймаут, HTTP 429 или 5xx автоматически повторяют только запрос генерации: максимум три попытки, до 90 секунд на один этап. Учитывается `Retry-After`; если указанная пауза выходит за общий бюджет, операция возвращает ошибку без немедленного повторного запроса. Отмена прекращает ожидание и дальнейшие попытки.

PR-сообщение обычно требует двух этапов: выбор сценария и анализ. Для выбора сценария передаются относящиеся к поиску документы и ограниченная история; полный diff не дублируется. Сам анализ получает полный разрешённый PR, инструкции skill и правила команды. Операция приложения ограничена 200 секундами; интерфейс ждёт до 220 секунд и показывает статус ожидания модели. Повтор генерации не перезапускает уже исполненный инструмент, не дублирует сообщение и не выполняет запрос ревью наставнику.

| Код | Поведение |
|---|---|
| `LLM_UNAVAILABLE` | После ограниченных автоматических попыток доступен повтор исходной операции с прежними ID/ключом. |
| `LLM_TIMEOUT` | Этап не завершился в отведённый бюджет; доступен повтор. |
| `LLM_CONFIGURATION` | Ключ, права или несовместимый запрос/модель: исправить серверную конфигурацию. |
| `LLM_INVALID_RESULT` | Некорректный JSON/function call, запрещённая функция/источник: доступен повтор без локальной подмены. |
| `SKILL_INVALID_RESULT` | Не прошли существующие проверки позиций, правил или контракта. |

Отправка наставнику выполняется только отдельным подтверждённым действием. Права, SHA, наставник и идемпотентность проверяются вне модели; неизвестный результат уточняется по исходной операции.

Если провайдер вместо одного обязательного function call вернул текст или несколько вызовов, адаптер один раз уточняет формат в пределах общего бюджета попыток. Непроверенный текст не публикуется. Запрещённые инструменты и ошибки конфигурации не повторяются автоматически. В журнале сохраняются номер попытки, длительность, статические коды причин и HTTP-статус, без ключей и сырых ответов.

## Проверки

`go test ./...` проверяет конфигурацию, отмену, ошибки и путь HTTP → очередь → LLM-адаптер → Git MCP → структурированный отчёт → подтверждённая квитанция. Тестируются передача skill, отказ для чужого PR, выдуманной строки и инструмента записи. Автотесты не вызывают внешний API; браузерные сценарии запускают Demo независимо от окружения.

Функциональный сценарий для выбранной модели — в [демонстрации](demo.md). Доступность и соблюдение протокола зависят от провайдера; неподдержанный ответ становится ошибкой операции, а не отчётом.
