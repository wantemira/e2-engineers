# Подключение внутренних скиллов

AI-Buddy вызывает внутренний скилл через MCP, а затем проверяет и сохраняет результат. В демонстрации корпоративный сервис реализован локальным mock-сервисом. Приложение и mock могут работать в одном процессе, но общаются через настоящий MCP HTTP транспорт с аутентификацией. Ключ генерируется при запуске и не передаётся браузеру.

## Что где хранится

| Часть | Назначение |
| --- | --- |
| `skills/<id>/skill.json` | ID и версия сценария AI-Buddy, контракт результата, внутренний скилл и его версия, необязательные фразы вызова. |
| `skills/<id>/SKILL.md` | Инструкции сценария. Передаются внутреннему скиллу при каждом вызове. |
| `teams/demo-backend/context.json` → `skills` | Список подключённых скиллов команды. |
| Там же → `capabilities.pr_review` | Выбор скилла для существующего PR-сценария. ID не зашит в service. |
| `mocks/skills.json` | Доступные версии mock-скиллов, разрешённые пользователи и имена исполнителей. |
| `internal/integration/mcpskills/executors.go` | Реестр реализаций mock-исполнителей. В нём нет ID конкретных скиллов. |

Настройки и инструкции читаются заново для новой операции. Изменение конфигурации не меняет сохранённые отчёты и квитанции. При изменении поведения следует поднять версию манифеста и инструкций. Хеш инструкций позволяет различить содержимое даже при ошибочно сохранённом номере версии.

Манифесты проверяются до работы скилла: ID, версии `major.minor.patch`, поддержанный контракт, непустые инструкции до 64 КиБ, отсутствие неизвестных полей, дубликатов и пересекающихся фраз вызова. Файлы инструкций читаются в пределах каталога скилла. Отсутствующая обязательная привязка `pr_review` останавливает загрузку конфигурации.

## Общий протокол

MCP endpoint — `/internal/skills`, инструмент — `execute_skill`. Все скиллы используют один транспортный конверт:

```json
{
  "skill": { "id": "internal-pr-review", "version": "1.0.0" },
  "contract": "pr-review.v1",
  "instructions": "Полное содержимое SKILL.md",
  "input": { "pr_number": 17, "head_sha": "полный SHA" }
}
```

Backend передаёт identity сессии через `X-Buddy-Actor` и служебную авторизацию. Параметры HTTP-запроса или сообщения не могут подменять пользователя, ID скилла, инструкции либо назначать наставника. На вызов выделено до 5 секунд, на операцию приложения — до 30 секунд. Отмена запроса передаётся по цепочке `context.Context`.

Ответ содержит `skill`, `contract`, `source` (`MOCK` либо `INTERNAL`), `run_id`, `instructions_sha256` и `output`. Приложение сверяет эти поля с запросом, проверяет типы и границы результата. Метаданные сохраняются в `skill_execution` отчёта и сообщения. Они доступны через `/workspace` и результат операции; интерфейс показывает понятную отметку mock-источника.

| Контракт | Вход | Выход | Использование |
| --- | --- | --- | --- |
| `pr-review.v1` | `pr_number`, `head_sha` | Те же номер и SHA, `checks`, `analysis` с замечаниями и оценкой границ проверки/задачи | Самопроверка и повторная проверка PR. |
| `message.v1` | `text` | `text` | Информационный ответ скилла в чате. |

В `pr-review.v1` mock сам получает разрешённый PR и CI через Git MCP. Приложение дополнительно сверяет владельца, репозиторий, SHA, статусы CI, позиции замечаний в сохранённом diff и командные правила. Ссылки на строки создаёт приложение. После вызова SHA читается повторно, чтобы пометить устаревший отчёт.

Оба контракта допускают только чтение. Ответ скилла не становится командой записи. Отправка PR наставнику проходит существующий отдельный путь с подтверждением, проверками прав и идемпотентностью.

## Пример нового скилла без изменения Go-кода

Для информационного скилла на существующем контракте:

1. Создайте `skills/release-guide/SKILL.md` с инструкциями, что объяснять стажёру.
2. Добавьте рядом `skill.json`:

```json
{
  "id": "release-guide",
  "version": "1.0.0",
  "contract": "message.v1",
  "description": "Объяснение последовательности первого релиза.",
  "target": { "id": "internal-release-guide", "version": "1.0.0" },
  "triggers": ["покажи маршрут релиза"]
}
```

3. Добавьте `release-guide` в массив `skills` конфигурации команды. Существующий `pr-self-review` и его привязку сохраните.
4. Добавьте объект в массив `skills` файла `mocks/skills.json`:

```json
{
  "id": "internal-release-guide",
  "version": "1.0.0",
  "contract": "message.v1",
  "executor": "fixture",
  "output": { "text": "После самопроверки согласуйте PR с наставником. Последующие шаги зависят от командного процесса релиза." }
}
```

5. Напишите в чате «Покажи маршрут релиза». Новый скилл вызовется через тот же MCP-клиент; ответ и сведения о вызове сохранятся в истории.

Это пример подключения, он не добавлен в рабочую командную конфигурацию. В тесте `TestAdditionalSkillNeedsOnlyFilesAndConfiguration` аналогичный второй скилл создаётся во временном каталоге и проходит полный HTTP → очередь → MCP → история путь. Тест также проверяет передачу изменённых инструкций и отсутствие локальной подмены при недоступности внутреннего ревью.

Существующие PR-запросы, повторная проверка и вопросы об учебном окружении имеют приоритет над информационными фразами скиллов. Фразы разных скиллов не должны пересекаться; свободное понимание намерений mock не имитирует.

## Как расширять реализацию

Новый скилл на поддержанном контракте добавляется файлами, без ветки в обработчике чата. Новая реализация mock-исполнителя требует отдельной функции-адаптера и записи в реестре `executors`; общий MCP-обработчик остаётся тем же. Для реального внутреннего сервиса реализуется порт `service.SkillRunner` и меняется подключение в `cmd/api`.

Новый тип входа/результата требует новой версии контракта, DTO и адаптера потребителя с проверками результата. Например, выкату потребуется отдельный сценарий подтверждения и квитанция. Универсальный текстовый контракт не даёт права выполнять произвольные корпоративные действия.

Markdown передаётся целиком и его хеш проверяется, но детерминированный mock не выполняет смысл произвольных инструкций. Манифест определяет исполняемую привязку, адаптер — поведение mock. Текущий адаптер ревью использует прежний анализатор только внутри mock-сервиса. Сервис приложения больше не вызывает `Assistant.Review`.

## Ошибки и проверки

`SKILL_UNAVAILABLE` означает отсутствие нужного подключения или версии; `SKILL_INVALID_RESULT` — несовпадение метаданных или повреждённый результат. `STALE_HEAD` и `NOT_FOUND` сохраняют прежний смысл. Сетевой сбой даёт `DEPENDENCY_UNAVAILABLE`. При отказе отчёт и запрос наставнику не создаются; скрытого перехода на локальное ревью нет.

Проверки запускаются обычными командами проекта: `go test ./...`, `go vet ./...`, `npm test` и `npm run test:e2e`. Backend-тесты используют настоящие локальные MCP HTTP соединения. Браузерный прогон проверяет и нормальный путь до квитанции, и недоступный скилл с последующим восстановлением.
